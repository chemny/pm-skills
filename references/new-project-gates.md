# 新项目交付与开工契约

本契约是workflow与artifact-contract的具体准入规则，适用于软件和Skill，不另立流程或状态账。主Agent必须在新建、接续及任何实施活动前读取；用户明确暂停、只讨论、只规划的约束优先。

## 1. 先分类，不用任务大小替换项目类型

项目入口为new/change/bug/single，使用形态为ui/cli/api/service/skill；模式为discussion/planning/execution。新项目不能通过拆成十行代码、小模块、搭脚手架等获得已有项目小修改的豁免。小修改须确有可引用的有效需求和设计，核本次差异。单项研究只交该项，不自动扩大为产品研发。

用户给出想法并回答几个问题后，通常下一步是整理PRD初稿、建议及尚待决定事项；不是继续无限问卷，也不是直接编码。回答本地处理、语言等问题，只认可对应决定，不批准未展示的整份PRD或设计。

## 2. 必交内容、形成时点与替代方式

八类一级与二级文件名称继续遵守artifact-contract。可以合并文件但不能省内容；合并须给出章节锚点、版本和责任索引。不生成空文件凑数，模板占位不能当满足。

| ID | 必须交付 | 最低内容 | 最晚时点 |
|---|---|---|---|
| A01 | project | 使用者、问题、首版目标/范围/非目标、约束、未知、资料入口 | 需求整理开始 |
| A02 | requirements（PRD唯一入口） | 需求ID、任务、触发、输入、处理/业务规则、输出、异常/取消/恢复、数据、质量、可观察验收 | 对应产品功能开发前 |
| A03 | product-design | 入口到结果的用户流程、关键状态/反馈、失败/恢复、决定与限制 | 对应产品功能开发前 |
| A04 | 原型或使用样例 | 核心成功与重要异常路径可被检查；标出模拟边界 | 对应使用设计收口前 |
| A05 | architecture | 模块、接口、数据/存储、隐私安全、错误处理、运行及风险/实验 | 对应实施任务前 |
| A06 | implementation-plan | 任务ID、输入版本、产出、依赖、修改范围、验证与DoD、执行条件 | 对应任务前 |
| A07 | validation | 测试方案、用例（前置/数据/动作/预期/标准）、需求和关键状态覆盖 | 对应实现任务前具备适用部分 |
| A08 | records/state、decisions、baselines | 决定来源、有效对象/范围/版本、唯一实际状态、阻塞和证据 | 启动后持续维护 |
| A09 | verification-report与evidence | 当前版本真实结果，分通过/失败/阻塞/未执行及限制 | 验收和交付前 |
| A10 | handover | 实际版本/位置、使用/配置、限制/恢复/接续 | 本次交付时 |

要求覆盖本轮实施范围，不冻结未来全产品。不能将A09/A10提前写成通过，也不能因它们还没形成而阻断正常产品设计。

## 3. A04按使用形态落实

- ui新产品：核心用户流程、关键状态与可演示核心操作的原型为默认必交。复杂核心交互应可操作；低风险局部可以静态稿。需要用静态方案替代整个可操作原型时，列理由、替代材料、遗漏风险，取得用户对该项简化的明确认可。
- cli/api/service：调用流程、契约与输入输出、错误/恢复样例必交，不强制造网页。
- skill：触发/不触发、澄清/等待/拒绝/失败/接续与输出样例必交，不强制UI。
- change/bug：可引用有效旧版设计和样例，补本次差异；不能把无基线的新项目写成小改动。

可操作原型可以含用于模拟交互的HTML等代码，属于prototype任务；不得连接真实模型、真实采集、正式业务写入而继续称其纯原型。技术实验与产品实现不因代码少而转为原型。

## 4. 三个交接检查点

G1产品方案：本轮范围与主要使用方式可审阅，A02/A03/A04有实质内容，重要产品选择获得用户认可。可以一次合并评审或继承真实逐项认可；不能用Agent签字、问答快照或文档status代替用户认可。未知只阻断受影响工作。探索原型允许在G1前形成，但须标明假设，不视为正式实现。

G2任务开工：有效输入、承重决定、设计、依赖、环境、工具、操作权限、验证八项均有依据；A01—A08适用部分可定位；本轮实施许可有效。G1不等于G2，完整环境就绪不弥补产品设计缺失。脚手架、空服务与基础模块只要是产品产物，也属于implementation。

G3交付验收：A09针对当前版本，逐项有真实判定，阻断项处理或范围明确变更；A10可照做接续。用户认可、工程验证与发布许可分别管理。

工程细节不逐份请用户盖章；此前只授权规划时，不自动转实施。任何暂停优先于此前宽泛推进授权，接续不会撤销暂停。

## 5. 真实性与实施边界

资料研究可以先行；编译运行探针、实际模型调用均不是只读资料检查。技术可行不批准产品，原型可点击不证明生产集成。没有明确实验范围和真实覆盖授权时，先提出实验方案，不能以“按流程推进”“合成数据”“本地运行”自行放行。具体实验与串并行规则按本契约后续章节及工程规则维护。

检查器验证结构与引用；主Agent核对内容是否充分和真实认可。提示词不是硬权限隔离，不得声称能拦截所有宿主工具。

## 6. 串并行、探索设计与认可范围

允许交错：需求整理与只读资料/环境检查；PRD初稿与探索性流程/草图；使用设计与技术方案草拟；需求细化与测试用例；工程计划与只读环境核查。探索稿写明假设，关键未决部分不定稿。原型模拟交互的代码不需要先完成整个G1，但必须有prototype任务、明确范围与模拟数据；不得真实采集、接模型或写正式业务数据。

必须串行：承重产品选择→受影响定稿/实现；主要使用方式认可→对应产品界面实现；关键实验通过→依赖该结论的实现；实际任务改动→对应版本验证；交付条件与发布许可→实际发布。原型转产品须新建implementation任务并满足G1/G2，不能原地改标签洗成已就绪。

并行任务必须引用明确输入、稳定共享接口、可协调写范围及集成责任。涉及同一文件/目录或接口未稳定时，先协调或串行；任务名不同不能证明独立。未决规则只阻断受影响任务，独立只读研究可继续；不得把“独立”写成逃避产品交接的理由。

真实产品认可关联scope（本轮功能/交互）、有效版本/哈希、已展示对象和用户原话来源。回答数据处理/语言等只批准该项；未展示的PRD/设计无认可。合并文档和多次对话可以承载同一认可，不强求每份文件签字；后续草案与有效基线并存，不能用新草案覆盖旧认可。变更后明确哪些任务与证据待重核，保持未受影响任务可用。

## 7. 提前实验准入：E01—E08同时满足

按动作而非名称分类：只读文档/已装版本/现有配置是research；模拟交互是prototype；编写或编译运行探针、调用本地/云模型、合成音频验证处理链是experiment；正式业务模块/脚手架/真实处理链是implementation。小段代码、本地运行、假数据、没有麦克风采集均不豁免实验。原型一旦连真实能力须重新分类。

| ID | 实验启动前必须明确 |
|---|---|
| E01 | 具体问题，关联需求/产品决定/项目目标 |
| E02 | 提前必要性：阻碍哪项选择，为什么只查资料不足 |
| E03 | 最小实验设计：输入、方法、预期输出、预先通过/失败标准 |
| E04 | scope及允许文件/命令/样本、运行次数/资源上限、停止条件 |
| E05 | 数据来源与流向、采集/外传/安装/付费/系统权限/配置等副作用 |
| E06 | 真实覆盖授权：用户原话、明确实验范围；泛化推进授权不足 |
| E07 | 独立experiment任务、依赖、八项执行条件、证据位置 |
| E08 | 返回产品决定的方式；不得用技术通过批准产品/交互/发布 |

完整PRD/原型前允许例外实验，但先呈现已知目标、具体阻断问题与最小实验方案/影响/停止条件，取得明确覆盖该实验的授权；已有明确覆盖授权持续有效，不重复形式询问。对未覆盖实验的“按流程推进”“保存实际结果”先给方案等待，不直接写探针。无技术阻断理由则回到PRD与使用方案，不为证明勤快而探测。

范围与结果分别记录：source与配置、样本、实际命令/次数、真实结果/缺口/证据。失败达到停止条件就停止，超出原次数/数据/安装/外传等边界须重新界定和取得授权；不能无限换模型/换路线追通过。测试失败不自动等于新的产品决定。

隔离实验默认放项目work/或专用实验目录；证据保留失败，不覆盖历史。实验产物转入正式产品要重新关联有效需求/设计，实施评审并补适用测试。实验通过只解锁所证实能力的依赖，不能把G1、产品质量、真实会议/长时/集成或发布状态写成已通过。

### E07记录一致性也是实验完成条件

必须在运行前登记有效输入快照/哈希与真实授权来源，给出task input_ids、decision_ids、依赖与八项条件。不得创建空inputs再写done，不得planned直接改done或随意自创记录字段。状态转换使用runtime.transition保留planned→ready→running→verifying→done（失败则blocked）并引用符合契约的当前对象证据；完成前evaluate/check_state和manifest引用检查均须通过。检查器不能证明语义，但形式不合法时不得宣称整个实验任务完成。

用户限制Python进程/调用次数时，仍须遵守以上记录契约：可以在唯一获准的Python进程内导入runtime、登记输入、合法转换、实际执行实验、保存原始输出/合规manifest并evaluate，不必为了记录再启动实验进程。若条件确实无法同时满足，先说明限制，不能略过记录要求。试验输出正确但状态/证据不合规时，应分开报告“实验观察通过、任务记录未通过”，修复记录问题不能覆盖原失败批次。

## 8. 执行前与执行后核对

实施入口统一先看具体task的can_start及阻塞，不得从valid=true/命令退出0/旧检查截图放行；v1可读不可据此新执行。动作、有效交付版本/认可、命令与修改范围、次数和停止条件绑定任务。public record_evidence与runtime.record进行执行时重核；不得改用内部_record_command、直接shell、脚本或apply_patch来绕过缺失准入。直接宿主工具也必须有当前任务的开工依据及完整实际轨迹，完成后核差异与语义。

资料/状态变化后重新检查；运行前后的文件与任务核对，未登记代码/运行记录或超范围变化按偏差报告并阻断受影响任务。退出0但业务断言失败时，保留原始结果，任务/验收不得记通过；技术、原型、产品、发布结论分别表达。真正用户暂停优先于早先推进授权，未收到明确恢复时不继续排队动作。

确定性守卫只约束调用它的入口，不能认证用户身份、评判全部需求/设计或拦住所有宿主工具。真实宿主测试须核实际工具轨迹和文件变化；不能用静态关键词证明不会跳步。

### 文档初始化不构成编码例外

新项目没有state时，允许在用户已授权资料位置先保存原始请求/授权快照和最小v2 documentation任务（inputs/decisions/context/八项条件），然后核具体任务继续PRD/使用方案。只为建立交接与状态，不得创建正式模块、编译探针、调用模型或连接真实能力；暂停时不初始化。合成UI原型有独立prototype任务与模拟范围，默认应位于docs/specs/experience/prototypes，不能借初始化执行。用户认可未形成时，资料草案仍可推进，产品实施保持等待。
