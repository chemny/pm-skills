# 主流程与交接

适用软件和Skill；入口分新建、已有变更、Bug、单项；模式分讨论、规划、执行。接续不是新建项目。主Agent负责整体目标、授权、整合和验收，实际方法按需加载。

| 职责 | 输入与工作 | 交接与进入条件 |
|---|---|---|
| 1 目标与基线 | 用户目标、现状、代码/规则/测试、限制、未知 | project；本工作项范围清楚，下一步承重未知已定位 |
| 2 需求与验收 | 明确功能、规则、数据语义、适用质量及预期 | requirements；当前任务行为与验收可判断，决定有来源 |
| 3 使用设计 | 软件入口/界面或Skill调用、状态、输出与样例 | product-design；当前任务体验明确，必要可行性不再未知 |
| 4 架构与实施设计 | 模块、接口、物理数据、安全/性能/部署；必要实验 | architecture；足以指导当前任务，不要求全产品冻结 |
| 5 工程测试计划 | 任务ID、输入、依赖、范围、验证、集成、DoD | implementation-plan与validation；能判定每项是否就绪 |
| 6 执行准备 | 实际工具/配置/权限、依赖与测试入口 | plan执行条件、实际配置、state和证据；不是准备报告代替可运行 |
| 7 实施与持续验证 | 实现、检查、评审、修复、集成 | 实际产物、state/issues/evidence；完成依据指向集成对象 |
| 8 综合验证验收 | 逐需求/状态核真实结果与限制 | verification-report；工程、产品验收和发布权限分开 |
| 9 交付维护接手 | 可取得版本、使用说明、配置、限制、按需恢复 | handover、按需operations；实际交付有证据，本次有界结束 |

2/3/4交错深化，测试预期从需求开始准备，5/6可重叠。承重决定→受影响设计、必要可行性→依赖实现、上游任务→下游任务、实际改动→当前对象验证、授权与交付条件→发布必须串行。

独立任务只有在输入、接口和写范围清楚时才能并行。T1就绪、T2待选择且T3依赖T2时，T1可继续，T2/T3等待。不是整个阶段统一阻塞，也不是让下游猜未定规则。实际并行需当前宿主与用户授权，简单任务主Agent直接完成。

产品预期改变回需求/决定；实现缺陷回任务；接口/环境变化标受影响输入、任务和证据待重核。不整体无差别回市场研究，不以实现困难静默改产品。已批准探索仅覆盖明确范围，不自动升级重投入或发布许可。

已有有效基线的小修改可合并文档、引用旧版要求；新项目按new-project-gates交付本轮需求、使用设计与适用原型/样例，不得借“小任务”省略。市场研究与十九份独立附件仍按适用性。状态入口为docs/records/state.yaml；恢复先查实际工作区与已发生动作。详细字段和确定性检查由状态契约定义，文件存在本身不构成通过。

## 新项目交接的具体准入

必须按[new-project-gates](new-project-gates.md)落实A01—A10与G1/G2/G3。小任务可合并内容，不可用拆任务跳过新产品需求、使用设计和原型/样例。进入实现前有对应产品认可与任务开工依据；资料研究、探索原型不自动升级为实验或产品实现。
