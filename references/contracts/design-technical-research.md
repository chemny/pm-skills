# 设计与技术研究：从产品依据到可实现的体验

在确定新交互形态、制作设计稿／原型，或研究技术可行性时读取。产品调研回答“为谁、解决什么、为什么做”；本合同补齐“怎样使用、怎样实现”。不新增主交付物种类，不把某个案例的胶囊、页面或技术栈变成通用模板。

## 1. 按本次变化确定研究范围

| 场景 | 必须做什么 | 不强制做什么 |
|---|---|---|
| 全新产品／新交互形态 | 画稿前研究同类任务的实际界面、操作流程和平台惯例；提前排查影响核心体验的技术约束 | 不必在画探索草图前完成整个架构或所有 POC |
| 已有项目升级 | 先看当前产品、代码／组件、设计系统和研究基线；对新流程、过期依据及受影响平台做增量研究 | 不重跑无关市场研究，不无故替换既有交互规范 |
| Bug／小优化 | 核实实际与预期行为；交互、技术假设均不变时可复用有效依据并记录理由 | 不要求为文案修正或原行为恢复补整套竞品报告 |
| 只做技术／无界面项目 | 研究接口使用方式和实现约束，界面研究注明不适用 | 不制造界面、截图或原型 |
| 独立设计／技术任务 | 只补当前任务需要的输入；复用适用的已有资料 | 不要求先跑全套 MRD、用户故事或其他阶段 |

研究范围写明“新增研究／复用依据／不适用”及原因。复用须检查来源日期、平台／版本、对应任务与本次变化是否匹配；MRD 获批不等于界面或技术研究已完成。

## 2. 设计与交互研究：先看实际如何完成任务

外部研究遵循 [Deep Research Contract](deep-research-contract.md)。新形态的专项研究默认 standard；小范围增量可缩小矩阵。复用已有候选集，只针对缺口补查，不因进入设计就机械重做全市场枚举；按目标用户、平台、任务相似度和交互差异选深查对象并说明选择理由。无直接竞品时可用相邻任务与平台规范，但须标明不可类比之处。

对每个主查对象，用相同任务拆解以下内容；不可取得的材料记录缺口，不用营销描述补图：

| 观察项 | 应留下的证据与结论 |
|---|---|
| 使用环境与入口 | 目标平台、应用背景、唤起入口、首次引导与日常使用的区别 |
| 真实界面 | 实际查看的截图、官方演示关键帧或可定位的界面链接；标注来源、日期、版本（不可得则写未知）和观察方式 |
| 操作路径 | 同一任务从触发到结果的动作、焦点／窗口切换、确认、取消、结果去向；不能只列功能名称 |
| 界面结构 | 主窗口、浮层、工具栏、设置等各自职责；布局层级、信息密度、关键控件和视觉反馈；不照抄品牌装饰 |
| 异常与恢复 | 加载、空输入、失败、权限、失焦、重复触发、恢复等相关状态；未观察到不能写成竞品已有 |
| 平台与可访问性 | 适用的平台惯例、键盘／触控／读屏路径及关键限制 |
| 取舍 | 哪些做法适合当前产品、哪些不采用及理由；用户收益只是推断时明确标注，不冒充可用性测试 |

证据区分：实际操作、官方演示／截图观察、官方文字说明、第三方反馈和推断。文字说明可以证明操作说明存在，不能冒充看过实际界面；静态图不能证明动态流程。未安装客户端必须说清，但可靠的官方演示可以支持范围明确的桌面研究。登录、付费、安装或权限阻碍按授权处理，不擅自扩大操作范围。

把研究收敛成“任务 → 交互方案及可比较替代 → 依据与代价 → 推荐 → 使用者决定”。确认的是产品实际形态和主流程，而非单纯一张页面清单。已有明确决定不重复询问；只有改变核心行为或出现新的承重取舍时才请使用者决定。研究发现与已批准 PRD 冲突时，先提交差异与推荐，决定后再更新相关文件，不能静默改需求。

### 从观察到设计约束

逐家介绍不能替代横向分析。在同平台、同任务、同状态下对照：默认／可选位置、占用空间、常驻信息／控件、按需操作、快捷键／指针路径、结果去向与遮挡。区分默认态、展开态、首次引导和异常态，不能拼接不同模式的控件成为默认界面。缺少观察的格子标未知，不编造像素尺寸或用静态图证明动态行为。

在 Design 收敛为：**共同模式（支持对象）／分歧与适用条件／采用或偏离理由／可检查的项目约束**。样本共性不是全行业标准，也不自动证明更高效；用户要求作为产品决定，不包装成市场事实。

对偏离参考模式、扩大面积或增加操作的方案，记录：要解决的问题、较简单的替代、预期收益、遮挡／动作／注意力／学习／出错成本、验证方法。无明确收益依据时，用符合用户要求的较简单方案作基线；创新方案可作标明假设的对照，不静默替换默认方案。保留无障碍和快捷键冲突的替代路径，但不默认等于增加常驻按钮。

“紧凑、轻量、不打扰”须落实到适用的项目约束：状态对应的行数／尺寸边界、信息与操作显示时机、默认／可选位置、不得遮挡的任务区域。具体数值和控件由项目决定，不把单行、底部或无按钮写成通用模板。产品能力不等于可见控件；PRD 若锁死不合适的呈现，提出局部变更并取得决定，不盲从也不静默删能力。

## 3. 技术研究：关键风险提前，完整架构后续深化

**前置可行性检查**从产品形态或主流程拟定时启动，不必等界面和用户故事写完。针对会改变体验的能力查官方平台／API 文档、已有实现和本项目代码：权限与部署、焦点与系统集成、延迟／离线、隐私及数据流、关键外部依赖和成本。目标是识别承诺能否成立，不是提前锁死语言和框架。

对每个承重问题记录：关联需求／交互、候选路线、平台及版本限制、证据类型、性能与成本口径、对设计的影响、必要 POC 与通过条件。无法获知竞品内部实现时标未知，不能从外观推断架构；竞品做得到不等于本项目已验证可行。

**完整技术研究**由 tech-design 在需求与交互清楚后深化：复用前置结论，比较完整方案、模型／API／供应商、数据模型与接口、系统级成本及性能；不把前置调研当作已通过 POC。需要实测的结论，只能用真实代码／设备／样本结果验证。

- 缺口会改变本次产品形态或核心交互：先研究或做获授权的最小 POC，再定稿；无法解决时给替代方案，请使用者限定探索范围。允许制作标明假设的可行性探索原型，不允许称为已确认可实现设计。
- 仅影响工程细节、不改变当前体验决定：可留到 Architecture／研发，但写清依赖、验证方法和承担阶段。
- 执行 POC、调用付费服务、安装软件或申请系统权限须遵守当前授权；不把“研究”当成执行这些操作的通行证。

## 4. 交付与跨阶段继承

不强制新增 Research 主文档。小任务可在对应文档中记录；材料较多时在本工作项的研究附件中保存并链接，不另造第二份权威规格。

| 归属 | 写入内容 |
|---|---|
| MRD | 产品机会、竞品产品观察、设计与技术线索；不声称已完成专项研究 |
| Overview／PRD | 研究引起的产品形态、范围和主行为决定，注明用户是否批准 |
| Design | “设计依据”：界面证据、同任务操作对照、采用／不采用理由、选定交互及相关技术约束；链接 Prototype |
| Architecture | “技术依据与可行性”：前置检查、候选比较、POC 结果／未执行状态和对产品设计的影响；文档可早期起草、后续深化 |
| Tasks／Test-Plan | 研究留下的验证任务与依赖、主流程与异常验收；不把待 POC 项写成已解锁的普通开发任务 |

每项影响决策的结论连成：来源／观察 → 结论及边界 → 产品选择（已批准或待决定）→ 受影响需求／设计／技术约束 → 验证方法。产品、设计、技术的研究状态分别记录，不能用市场 research_gate 替代后两者；状态字段与兼容方式见 [流水线台账](../capabilities/pipeline-orchestration.md)。

## 5. 画稿前与交付前检查

画稿前核对：研究范围有记录；相关形态有实际界面证据和任务流程；影响体验的技术问题已研究或明确限定探索；核心交互已获决定；与 PRD 的冲突没有被跳过。缺可查证据就补查，缺用户选择就给推荐和替代，不以文档齐全放行。

原型须在真实使用情境中表现主任务：页面、浮层、命令行、后台服务等按产品形态选择，不能“一条需求一个页面”或“一种状态一个页面”。状态切换器、PRD 编号和导航目录属于评审辅助，不是产品主界面。

交付时分别报告：① 研究证据与决策是否充分；② 主任务体验是否合理、是否造成不必要跳转；③ 原型交互是否正常；④ 技术可行性是否实测。浏览器点击测试通过不代表设计合理，也不代表系统集成已验证。

将参考模式、批准约束和原型同状态对照，记录符合／不符合／未检查：关键内容遮挡、信息是否此刻必需、重复操作、键盘主流程是否被迫切换鼠标、展开／收起时机。检查典型窗口和缩放，按平台补安全区／多屏；评审工具不得挤占产品布局而混淆结论。视觉受阻仍做规格和代码一致性检查，但不报告视觉通过。

仅有截图链接、逐家介绍或以后测试列表，不足以支持具体默认布局；缺少会改变默认布局／操作的比较时，本项研究保持 revise。状态单测和文档关键词校验不能代替设计判断。规则改造用已知失败稿和适用范围不同的反例走查，验证能拦住问题又不强制所有产品采用同一形态。

前置资料检查不授权代码实验。写/编译探针、实际模型调用或合成音频处理均按new-project-gates E01—E08准入；先明确问题、必要性、样本/判定、资源/停止、数据副作用与真实覆盖授权。完整PRD/原型不是获准最小实验的必需前置，但技术成功不代替产品认可。
