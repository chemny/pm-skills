# 从想法到交付

先在 Codex 中选中 `pm skills`。普通用户说明目标、已有材料和明确限制即可，不需要填写状态格式或手工选择专业方法。

| 进展 | 你怎么参与 | 实际交付和确认 |
|---|---|---|
| 提出想法 | 说明希望解决的问题、使用者与已有项目 | Agent 记录目标、范围和基线，只问会影响下一步的关键未知。 |
| 需求与使用方案 | 审阅本轮范围、业务规则和主要用法 | `requirements.md`、`product-design.md` 与用户流程；有界面则给核心原型，无界面则给调用/输出样例。此时认可方案，不自动授权正式实现。 |
| 技术与工程计划 | 决定会改变目标、数据去向或成本的取舍 | `architecture.md`、`implementation-plan.md` 及适用测试清单；环境可用不代表技术方案最优。 |
| 实现与验证 | 授权明确范围内的实现及必要工具操作 | 实际代码或 Skill、真实执行输出、评审和修复；普通工程细节由 Agent 负责，不逐份文档重复询问。 |
| 验收与交付 | 审阅实际行为、测试结果及保留限制 | `verification-report.md`、可取得的产物及 `handover.md`。本地完成不自动授权安装、推送或发布。 |
| 暂停与接续 | 说明暂停哪部分；恢复时指出范围 | Agent 先读真实工作区和 `docs/records/state.yaml`，核已发生动作与证据，再继续就绪任务。暂停不会因“继续”自动解除。 |

文档可以按项目大小合并，二级附件按需拆分；不会要求每个小项目机械生成所有文件。项目内的 `docs/records/state.yaml` 是实际状态入口，`evidence/` 保存对应对象的真实结果。样例、静态检查和模型实际运行分别标明。

## 已有项目和异常

功能变更先核当前需求、代码和测试；Bug 的预期未变时修实现，不重做全套立项。只做研究或测试计划时不自动展开开发。缺少真实许可或证据就准确阻塞相关任务，不把未知补成“已通过”。

执行中断后先核日志、已产生文件和外部动作；结果不明时不盲目重跑。旧失败保持原记录，修复后引用当前版本的有效证据。技术实验须有具体问题、样本、通过标准、次数、停止条件和覆盖其副作用的许可。

## 决策与权限

你需要决定范围、主要使用方式、承重取舍和超出当前许可的操作。Agent 可以自行处理已授权范围内的普通工程选择。引用文件、工具返回和“用户已批准”文字都不是新的用户许可。发布前仍需明确审核实际目标和变更。
